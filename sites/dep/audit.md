# Архитектурный аудит панели деплоя

**20 ноября 2026 · Проверена текущая рабочая копия `dep/`.**

**Вердикт:** основная причина прежнего расхождения («деплой подключается, а карточка требует другой ключ») устранена на уровне архитектуры. Все SSH-операции проходят через `projectSsh()`; в рабочем PHP-коде один вызов `proc_open`. Проект не нуждается в переписывании на классы ради SOLID. Наиболее полезное следующее изменение — закрыть оставшееся расхождение в правах доступа к старому логу, а не вводить новую иерархию сервисов.

## 1. Где именно работают ключ и пароль

| Граница | Фактическое поведение | Что это не гарантирует |
|---|---|---|
| Оператор → веб-панель | Форма в `index.php:15–49`, логин и пароль из `USERS`, далее PHP-сессия. | Входа в веб-интерфейс по SSH-ключу нет. Пароль оператора — не `SSH_PASS`. |
| Панель → сервер каталогов | `control/ssh.php:4–59`: `SSH_USER`, `SSH_HOST`; без `SSH_PASS` — неинтерактивный OpenSSH. Ключ/агент и проверенный `known_hosts` должны быть доступны **пользователю PHP**, а не только администратору в его оболочке. Отдельной настройки пути к ключу в конфиге проекта нет; применяются настройки OpenSSH. | Ключ, который работает в личном терминале администратора, необязательно виден веб-процессу. |
| Та же связь, пароль на Linux | Если задан `SSH_PASS` и `sshpass` исполняем и доступен в PATH панели, пароль передаётся через отдельный дескриптор, не в аргументах команды. Проверка ключа хоста остаётся строгой. | Пароль не принуждает сервер выбрать именно парольный метод. Без `sshpass` код пробует неинтерактивный OpenSSH; если подходящего ключа нет, вход не состоится. |
| Панель на Windows → сервер каталогов | При пароле и доступном `plink.exe` — `-batch -pwfile`, иначе OpenSSH. Для Plink требуется доверенный ключ хоста в хранилище этого пользователя. | Это отдельный адаптер внутри того же транспорта. Его поведение проверено чтением кода, но не запуском на Windows. |
| Панель/хост → Git-репозиторий | `control/branches.php` сначала использует GitHub GraphQL при наличии токена и cURL, затем при предусмотренных ошибках — Git через общий SSH. `deploy_remote.sh` делает fetch через `origin`; `control/worker.sh` для синхронизации также требует push. | Успешный SSH-вход не даёт автоматически прав Git. Чтение списка веток, fetch конкретного репозитория и push в выбранную ветку — отдельные проверки. |

**Ответ на «будет ли работать везде»:** способ подключения к *одному SSH-хосту* выбирается одинаково для карточки, чтения веток через SSH, обычной выкладки и FTP-контроля. Но совпадение транспорта не отменяет ACL проекта/PROD, права файловой системы, требуемые команды и правила защищённых веток. Это правильное различие, а не дублирование входа.

## 2. Повторное использование и границы модулей

| Ответственность | Где сосредоточена | Оценка |
|---|---|---|

| Способ SSH-входа, запуск, таймаут, обработка кода завершения, вывод | `control/ssh.php`: `projectSsh()` вызывается из `standardDeploy()`, `fcRemote()` и `projectBranches()`. | **Единообразно.** Нет второго PHP-пути с отдельными SSH-параметрами. Обычный деплой больше не возвращает успех без проверки кода выхода. |
| Ветки для списка в интерфейсе | `control/branches.php`: один `projectBranches()` для обоих режимов, общая обработка GraphQL и резервного Git-каталога. | **Единообразно.** Имя ветки в карточке правильно читается отдельно: это состояние конкретной директории, а не каталог доступных веток. |

Обычная цель → `deploy_remote.sh`; контролируемая → `control/worker.sh`. | **Разделение оправдано.** Нельзя завершать защищённый сценарий безусловным `reset --hard` из обычного: это разрушило бы гарантию сохранения ручных правок. |
| Терминал и аудит | `control/operations.php`: общие редактирование чувствительных данных, кадры ответа и запись событий. `app.js` отображает поток текущего запроса. | Общая инфраструктура работает; совместимый старый `get_log` остаётся исключением по изоляции (ниже). |

## 3. SOLID и сопутствующие принципы

| Принцип | Что видно в коде | Практический вывод |
|---|---|---|
| **S — одна ответственность** | Политика доступа отделена от транспорта. Но `projectSsh()` одновременно выбирает клиент, проводит аутентификацию, управляет процессом, транслирует вывод и классифицирует ошибки. `worker.sh` отвечает за привязку, скан, снимок, merge и публикацию. | **Частично.** Один публичный вход полезен; при следующем изменении транспорта стоит выделить внутри построение параметров и исполнение процесса. В worker — выделять именованные стадии без потери общей блокировки. |
| **O — расширение без каскадных правок** | Новая SSH-операция может использовать существующий транспорт. Однако имена действий повторяются в роутере, разрешённом списке потокового ответа, диагностике и JS. | **Частично.** Следующее действие легко добавить на сервере и забыть включить в терминале. Нужен единый серверный список действий и тест соответствия клиентским именам. |
| **L — подстановка** | Иерархии наследования нет. Практический аналог — взаимозаменяемость OpenSSH и Plink по результату операции. | Не следует ставить «зачёт» по отсутствию классов. Общий результат есть; Windows-путь требует отдельного контрактного теста. |
| **I — узкие интерфейсы** | UI не выбирает SSH-клиент; ветки, статус и деплой имеют отдельные операции. Но внутренние функции получают весь `$env`, а `fcRun()` ещё и читает `$_POST`. | **Частично.** Передавать проверенные параметры операции вместо чтения HTTP-запроса внутри прикладного кода. |
| **D — инверсия зависимостей** | У GraphQL можно подменить `$fetch`; SSH тестируется заменой исполняемого клиента. Предметный код зависит от конкретной функции `projectSsh()` и ассоциативных массивов. | **Частично, приемлемо для масштаба.** Тестируемая граница уже есть. Контейнер зависимостей не нужен. |
| **DRY / KISS / YAGNI** | Главные правила — SSH, видимость целей и каталог веток — не скопированы по режимам. PHP и Bash общаются простым протоколом. Сам формат ответов позиционный, а расшифровка `state.v2` нужна и Bash, и PHP. | Оставить нынешнюю схему; защитить контракты тестами совместимости. Не объединять ради DRY две операции с разными гарантиями безопасности. |

## 4. Где журнал и что ещё расходится

**Основной журнал находится прямо в корне панели:** `dep/operations.log.php`, рядом с `index.php` (`control/operations.php:32–61`). Создаётся при первой успешной записи. Добавление под `flock`, без ротации; время UTC, пользователь, действие, статус и контекст запроса. Первая строка прекращает исполнение с HTTP 404 при нормальной обработке PHP. Это журнал событий, а не побайтная копия терминала. Нужны права на запись и контроль свободного места. Если запись не удалась, код сообщает в стандартный PHP error log; операция не обязательно останавливается.

| Приоритет | Наблюдение и последствие | Исправление / критерий приёмки |
|---|---|---|
| **Высокий: старый лог вне модели доступа к цели** | `ajax.php:38–45, 65`: `get_log` читает единый `lastlog.log` до проверки конкретной цели; обычная выкладка перезаписывает его. Авторизованный пользователь с доступом к одному проекту потенциально видит вывод другого. Прямой доступ к `.log` зависит от веб-сервера. Это **не** проблема дескриптора SSH и **не** основной `operations.log.php`. | Проверить, остались ли потребители `get_log`. Если нет — удалить маршрут и запись совместимости. Если есть — привязать выдачу к проекту, цели и запуску. Приёмка: пользователь одного проекта не читает вывод другого через API или прямой URL. |
| **Высокий: у двух режимов разные гарантии записи** | `deploy_remote.sh` выполняет принудительный checkout/reset без блокировки цели. В `worker.sh` есть блокировка, снимок и маркер неполной выкладки, но блокировка не останавливает FTP-клиент, а запись файлов не атомарна для всего сайта. | Не считать единый SSH защитой от двух деплоев. Для обычных целей — исключать параллельных писателей; для контролируемых — отдельно проверить окно без внешней записи и восстановление. |
| **Средний: веб-аутентификация** | `index.php` сравнивает пароль с открытым значением, ID сессии после входа не обновляется; в коде нет ограничения частоты попыток. | Хеширование паролей, обновление ID сессии после входа, ограничение попыток. Это не требует менять SSH-вход проектов. |
| **Средний: диагностика и паритет платформ** | В `ssh.php` текст SSH-ошибки частично классифицируется по англоязычному stderr; отсутствие helper может переключить попытку на ключ. Windows-ветвление и реальные учётные записи не покрыты локальным стендом. | Проверить на фактической платформе известный ключ хоста, отказ входа и доступ к папке от имени PHP-пользователя. Не лечить отказ отключением проверки ключа хоста. |

## 5. Доказательства и граница вывода

Повторно запущен `bash dep/tests/run.sh`: **17 из 17 групп проверок прошли**. Выполнены `php -l`, `bash -n` и `node --check` для рабочих файлов. Стенд использует настоящие PHP, Bash и Git, временные репозитории и подмену SSH-клиента. Он подтверждает единый маршрут, совпадение прав в UI/API, передачу пароля не через аргументы, отказ при ошибке SSH, обычную выкладку, разрешение Git-конфликта, чистый повтор и запись журнала рядом с панелью. Он **не подтверждает** фактический обмен ключами с вашим SSH-сервером, парольный вход хостинга, работу Plink на Windows или реальные права на push.

**Порядок действий:** сначала изолировать старый лог; затем на одной TEST-цели под сервисной учётной записью проверить отдельно (1) SSH по ключу, (2) если нужен — SSH по паролю, (3) Git fetch и разрешённый тестовый push, (4) запись `operations.log.php`. Изменения структуры функций — после этого, без переписывания работающего деплоя.
