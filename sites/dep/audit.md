# Аудит панели деплоя · 20 ноября 2026

> Исторический снимок до переноса обработчика на Bash. Ссылки на `worker.py` и результаты ниже относятся к прежней реализации; актуальные зависимости, тесты и ограничения — в `CONTROL.md`.

**Вывод:** контролируемый режим можно проверять на `abhaz_test` в окно обслуживания. Он защищает от двух одновременных запусков панели и сохраняет ручные правки до слияния, но **не блокирует запись через FTP и не переключает весь сайт атомарно**. На остальные директории эти гарантии не распространяются. Для обычного PROD-деплоя главный нерешённый дефект — панель показывает успех, не проверив, завершился ли Git без ошибки.

## Границы и результаты проверки

Проверена текущая рабочая копия панели: вход, права, выбор проекта и цели, получение веток, привязка Git, контроль файлов, синхронизация, оба пути деплоя, обработка ошибок и журналирование. Флаг включён только для `abhaz_test`. В `control/api.php:14–17` операции нового режима для `prod` запрещены сервером, а не только скрыты в интерфейсе.

**Повторно выполнено:** 7 из 7 локальных тестов прошли (`python3 -m unittest discover -s dep/tests -v`). Проверки синтаксиса прошли для `index.php`, `ajax.php`, `control/api.php`, `accet/js/app.js` и обоих Bash-скриптов. API проверялся с подменой SSH-транспорта; Git — на временном локальном репозитории. Проверялись, в частности, сохранение правок при конфликте, ручное разрешение и повтор, запрет записи в чужую ветку, реакция на занятую блокировку и отсутствие новых коммитов при чистом повторном деплое. Проверка маркера незавершённой выкладки — не испытание восстановления после реального обрыва питания. На хостинг не подключались, реальный FTP, права веб-сервера, браузер и доступность сайта после выкладки не проверялись.

## Что гарантирует каждый режим

| Ситуация | `abhaz_test` с контролем | Цели без режима |
|---|---|---|
| Два оператора меняют одну цель | Неблокирующий `flock`; второй получает «Цель занята» при общем файле блокировки | Блокируется кнопка в одном окне, но не второй процесс |
| В каталоге ручная правка отслеживаемого файла | Снимок перед merge; при конфликте Git хранит снимок, выкладка не начинается | Принудительные checkout/reset могут затереть правку |
| Изменился удалённый репозиторий | Результат слияния отправляется без force; публикуется конкретный SHA | Цель берётся из `DIRS`, но соответствие `origin` репозиторию проекта и итоговый `HEAD` не проверяются |
| Обрыв при записи файлов | Маркер `incomplete.json` запрещает новые операции до ручной сверки | Нет маркера; повтор не восстанавливает несохранённые правки |
| Результат в UI | Успех требует ответа worker и успешного завершения транспорта; файлы сверяются с деревом Git | `ajax.php:404–408` возвращает `ok` после `shell_exec` без проверки кода выхода |

## Новый режим: замечания по приоритету

**1. Высокий — FTP может записать файл после последней проверки.** `control/worker.py:68–101, 552–604`; `control/api.php:20–29`. Блокировка лежит в домашнем каталоге SSH-пользователя. Она защищает участников, использующих тот же файл, а не FTP, cron или другую учётную запись. Подтверждение «запись остановлена» — заявление оператора. Повторный скан обнаруживает часть гонок, но между ним и заменой файла остаётся окно. **Условие пилота:** один владелец публикации, фактическая остановка внешней записи, завершение открытых передач. При проверке пересечений учитывать, что два разных значения `SSH_HOST` могут указывать на один хост.

**2. Высокий — при частичной выкладке маркер защищает Git, а не доступность сайта.** `control/worker.py:575–615`. Файлы заменяются по одному, затем выполняются удаления, обновление метаданных клона и итоговый скан. Если поздний шаг упадёт, часть сайта уже изменена. Автокоммит этой смеси блокируется правильно; автоматического отката нет. **Действие:** до первого использования проверить восстановление из копии по `CONTROL.md`. При маркере не повторять деплой и не отключать флаг в обход проверки.

**3. Высокий — лимит 32 МиБ проверяется слишком поздно для входящего файла.** `control/worker.py:330–337, 553–604`. Сканер отклоняет крупный файл на диске, но при подготовке входящего Git-объекта размер не проверяется: blob целиком читается, записывается в рабочий каталог, и лишь итоговый скан применяет лимит. Так корректная ветка с крупным файлом может перевести цель в состояние незавершённой выкладки. **Исправление:** проверить размеры входящих объектов и свободное место до изменения сайта и создания маркера. Критерий — отказ на предварительной проверке, прежние файлы нетронуты. Это вывод по коду, не наблюдавшийся отказ хостинга.

**4. Средний — успешный push и успешная выкладка не одно событие.** `control/worker.py:500–557`; `control/api.php:34–39`. Снимок и merge могут уже попасть в remote, а повторный скан, публикация или ожидание SSH — завершиться ошибкой. UI не всегда показывает, какой шаг последний подтверждённый. **Исправление:** сообщать раздельно SHA сохранённого снимка, результат обновления ветки и результат публикации; при потере связи указывать идентификатор операции для сверки. Не повторять push, ориентируясь только на сообщение браузера.

**5. Средний — совпадение файлов с Git не подтверждает доступность сайта.** `control/worker.py:580–609`. Замена через временный файл создаёт новый объект файловой системы. Код переносит обычные биты чтения/записи и признак исполнения, но не копирует владельца, прежнюю группу и индивидуальные ACL. Сверка содержимого проходит от имени SSH-пользователя. **Приёмка:** подтвердить на TEST чтение заменённых файлов именно веб-сервером и запись именно FTP-пользователем, в том числе в новых каталогах.

**6. Средний — зелёный статус привязки не означает полной проверки базы.** `control/worker.py:243–255, 275–302`. Для существующего клона кнопка становится зелёной по локальному `HEAD` и подходящему `origin`; проверка наличия ревизии в истории remote происходит позднее. Это не ведёт к тихой записи: следующий шаг может отказать. Различать «репозиторий распознан» и «база подтверждена», либо отложить зелёное состояние до полной проверки.

**Ограничения, не дефекты:** `FTP_WRITE_BRANCHES` управляет *записью* в ветку, а не разрешением читать её или выкладывать чистую ревизию. В пилоте запись разрешена в `test` и `test/*`. Пустой `FTP_NEW_FILES` не мешает фиксировать изменения отслеживаемых файлов, но не позволяет автоматически добавить произвольный новый файл. Контроль фиксирует итоговую разницу в содержимом, а не каждое действие FTP-пользователя. Два чистых деплоя без внешних триггеров не должны создавать новые коммиты; это проверено локально.

## Очерёдность действий

1. **До первого TEST-деплоя:** подтвердить путь FTP/SSH, права обеих учётных записей, проверенный ключ хоста, окно без внешней записи и работоспособную резервную копию. Сделать первую привязку и контроль без публикации; сверить списки изменений и удалений с владельцем сайта.
2. **На TEST:** проверить конфликт и ручное разрешение, параллельные запросы из двух сессий, обрыв во время замены файлов и восстановление. Проверить отказ до записи при превышении лимита; отдельно открыть сайт через веб-сервер после успешного деплоя.
3. **Для существующих PROD-целей:** в первую очередь устранить ложный успех, проверить транспорт и изоляцию журналов. Успех тестов `abhaz_test` не является подтверждением надёжности этого отдельного пути.
