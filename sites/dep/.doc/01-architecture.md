# 01. Архитектура и конфигурация

Панель PHP управляет Git-выкладкой на удалённый хостинг. Браузер не связывается с SSH или GitHub для выкладки напрямую. PHP проверяет доступ и запускает фиксированную команду `bash -s` по SSH; проверенный сценарий и параметры передаются через stdin. Git и операции с файлами выполняются на хостинге. Трафик `push` идёт с хостинга прямо в GitHub.

## Карта кода

| Файл | Назначение |
|---|---|
| `index.php` | Сессия, вход, список доступных проектов, карточки целей, интерфейс |
| `accet/js/app.js` | AJAX, управление состояниями кнопок, потоковый терминал, прогресс, подтверждения |
| `ajax.php` | Маршрутизация, ACL, CSRF и выбор обычного либо защищённого пути |
| `control/project.php` | Чтение конфигов и интерпретация целей `DIRS` |
| `control/branches.php` | Список веток: основной путь через GitHub GraphQL, при необходимости SSH/Git; служебные ветки скрываются |
| `control/api.php` | Параметры защищённых операций, проверка подтверждения, разбор ответа Bash |
| `control/ssh.php` | Запуск OpenSSH или Plink, проверка хоста, раздельная обработка stdout и stderr, ограничение длительности |
| `control/inspect.sh` | Проверка каталога, `HEAD`, ветки, привязки и прерванной выкладки |
| `control/worker.sh` | Сканирование, снимки, слияние, push и публикация |
| `deploy_remote.sh` | Обычная выкладка без обратного коммита |
| `control/operations.php` | Потоковые события, маскирование секретов и журнал |
| `tests/run.sh` | Офлайн-стенд с локальными Git-репозиториями и подменой SSH |

## Доступы и параметры

- `.env`: `USERS` — учётные записи панели. В текущей реализации файл содержит значения паролей, поэтому его нельзя отдавать через HTTP или включать в публичный архив.
- `projects/<project>.env`: `DIRS` определяет имена целей, абсолютные каталоги и тип `test` / `prod`; `ALLOWED_USERS` и `PROD_ALLOWED_USERS` задают доступ. Сервер проверяет права независимо от видимости кнопок.
- `FTP_CONTROL_TARGETS`: включает защищённый режим для перечисленных целей. В текущей конфигурации это `abhaz_test`. Защищённый обработчик не разрешён для PROD. Остальные цели используют обычный деплой.
- `SSH_HOST`, `SSH_USER`, `SSH_PASS`: соединение панели с хостингом. Проверку ключа SSH-хоста не отключать. На Linux при наличии `sshpass` пароль передаётся через файловый дескриптор, не в командной строке.
- `REPO_URL`, `GITHUB_TOKEN`: адрес репозитория и токен проекта. Токен используется для каталога веток; для защищённой синхронизации/деплоя он передаётся хостингу и используется при HTTPS push. Без него push использует доступ Git на хостинге. Для `fetch` рабочего сценария хостингу по-прежнему нужен доступ чтения. GitHub определяет права push по владельцу токена, а не по SSH-пользователю.
- `GIT_COMMIT_NAME`, `GIT_COMMIT_EMAIL`: автор и коммитер новых коммитов; это не аутентификация GitHub и не криптографическая подпись.

## Состояние на хостинге

Вне каталога сайта, под `$HOME/.dep-control/<ключ цели>/`, хранятся `state.v2`, служебный Git-репозиторий `repo`, кэш выбранных веток `control-cache`, блокировка записи и временные каталоги операций. Ключ цели зависит от абсолютного пути сайта. `state.v2` хранит адрес репозитория, базовый SHA, последний FTP-снимок, ожидаемый `HEAD`, флаги пустой цели и активного снимка, имя последней опубликованной ветки. `incomplete.json` сигнализирует о незавершённой публикации, а не об успешно выполненном откате.

Контроль и неподтверждённый предпросмотр используют временный репозиторий. Они могут читать локальные Git-объекты, но не держат блокировку записи цели. У обновления кэша есть отдельная блокировка. Привязка и подтверждённая запись взаимоисключающие.

## Интерфейс и терминал

Браузер получает поток событий и итоговый JSON в рамках AJAX-запроса. Команды и этапы окрашены отдельно от обычного вывода; важные различия и подтверждения выделены жёлтым, успех — зелёным, ошибка — красным. Фоновые запросы карточек не засоряют лог. Подтверждения отображаются у терминала. Полоса показывает реальные счётчики там, где известен объём работы, и неопределённый прогресс в остальных случаях. При буферизации прокси таймер запускается сразу, но серверные сообщения могут появиться только в конце. Журнал на сервере и терминал вкладки — разные вещи.
