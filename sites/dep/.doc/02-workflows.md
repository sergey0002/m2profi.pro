# 02. Алгоритмы работы

## Обычный деплой

Если у цели нет флага защищённого режима, панель запускает обычную цепочку `fetch → checkout → reset`. Обратного коммита, проверки FTP-правок и специального подтверждения нет. Локальные изменения отслеживаемых файлов могут быть перезаписаны. Общее оформление лога не меняет этот алгоритм.

## Привязка защищённой цели

Существующая Git-копия распознаётся по `HEAD` и подходящему `origin`. Для каталога без `.git` оператор выбирает базовый SHA или вершину ветки, смотрит список расхождений и подтверждает привязку. Первоначальные удаления требуют отдельного подтверждения. Привязка не меняет файлы и не делает push. Пустая цель ждёт первой выкладки; синхронизация такой цели недоступна. До первой записанной выкладки базой служит подтверждённый SHA или `HEAD` распознанной копии.

## «Контроль» — только проверка

1. Взять базовый коммит выкладки и получить вершину выбранной ветки в локальный кэш. На прогретом кэше Git получает недостающие объекты, а не скачивает всю историю заново; сеть всё равно нужна для проверки актуальной вершины.
2. Собрать объединение путей двух деревьев. Лишние файлы вне обоих деревьев не перечисляются. Пути проверяются пакетно, содержимое нужных файлов читается и хешируется без записи Git-объектов в снимок.
3. Сравнить версию на сайте с обеими Git-версиями. Терминал показывает изменения из Git, ручные правки/удаления и коллизии. Указываются оба SHA. Результат не восстанавливает историю действий пользователя: он описывает состояние файлов на момент чтения.
4. Ничего не коммитить, не отправлять и не менять на сайте. Старый результат «Контроля» не является разрешением на последующую запись.

## Синхронизация и защищённый деплой

1. Получить выбранную ветку. Для привязанной цели загружается выбранная ветка, для первичной проверки истории существующей Git-копии могут проверяться все ветки.
2. Собрать снимок **только управляемых путей**: из базы выкладки и последнего сохранённого FTP-снимка. Отсутствующий на сайте файл, добавленный только разработчиком в новой ветке, не считается FTP-удалением. Посторонние новые файлы не отправляются и не удаляются. Признак исполнения и сырые байты участвуют в сравнении.
3. Для деплоя проверить занятые пути выбранной ветки. Неуправляемый отличный файл или папка на входящем пути блокирует выкладку. Уже существующий обычный файл с совпадающим хешем и битом исполнения не перезаписывается. `robots.txt`, созданный по FTP, остаётся на месте, пока ветка не пытается занять этот путь другой версией.
4. Если отправлять нечего, синхронизация завершится без push. Деплой того же SHA и чистого дерева при отсутствии ожидающего снимка завершается после первой проверки без подтверждения. При другом SHA с тем же деревом после подтверждения обновляются только метаданные.
5. Для остальных операций показать список файлов и целевую ветку. До подтверждения нет push или изменения сайта. Ответ подписан серверным ключом сессии и ограничен проектом, целью, пользователем, действием и веткой. После «Да» сверяются заново вершина, дерево, база и состояние снимка. При изменении данных нужен новый предпросмотр. Тяжёлый снимок между запросами **не сохраняется**.
6. Проверить типовые чувствительные имена. Собрать новый коммит от сохранённого снимка и подготовить слияние локально. Если слияние конфликтует, сохранить только служебный снимок в `ftp-snapshots/*`, вывести конфликтующие пути и остановиться. Целевая ветка и файлы сайта не перезаписываются.
7. При успешном слиянии **для деплоя** сначала проверить итоговые пути и повторно сверить сайт. Затем сохранить снимок и при необходимости обновить выбранную ветку без force-push. При успехе синхронизации работа заканчивается: файлы сайта она не выкладывает.
8. Для деплоя отметить начало публикации, заменить целевые файлы по одному и удалить только управляемые пути, отсутствующие в итоговом дереве. Для существующей Git-копии обновить `HEAD` и индекс при необходимости. Проверить итоговое дерево, записать новый SHA, снять маркер прерванной выкладки.

### Пример

Сайт был выложен из `master`. По FTP поправили `index.php`, а `task_new_site` добавила `new.php`. «Контроль» покажет ручную правку `index.php` и входящее изменение `new.php`. После подтверждения защищённый деплой перенесёт правку в `task_new_site`, если Git сможет объединить изменения, затем выложит итог. Исходная ветка `master` от выбора `task_new_site` не обновляется. Файл `123123`, появившийся вне управляемых путей и не нужный входящей ветке, остаётся на сайте и не попадает в Git.
