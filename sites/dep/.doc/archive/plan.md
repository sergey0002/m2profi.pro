# План: контроль ручных правок перед деплоем

**Статус: проект решения, без изменений в работающей панели.** Единица настройки — **целевая директория**, не проект. Цель режима — не затереть файлы, которые изменили на сервере в обход Git. Для выбранной цели предусмотрены три кнопки: **«Привязать к Git»**, **«Контроль»** и **«Синхронизация»**. Привязка однократная; перед очередным деплоем контроль и синхронизация выполняются автоматически. Конфликт останавливает выкладку, но не уничтожает ни работающие файлы, ни коммит с ручными правками.

## 1. Как включить для одной директории

Предлагается **не менять синтаксис `DIRS`**, а добавить необязательную строку в конфиг конкретного проекта. Иллюстрация, не изменение реальных конфигов:

```ini
DIRS=Тест:/srv/example/test|test,Публикация:/srv/example/live|prod
FTP_CONTROL_TARGETS=Публикация
```

Значение — имена целей из `DIRS`, разделённые запятыми; совпадение точное после удаления крайних пробелов. Отсутствующее или пустое поле означает «все цели работают как сейчас». В примере новый режим работает только для «Публикация». Тип `prod` сам по себе режим не включает. При опечатке, дубликате имени или двух именах для одного физического каталога с разной политикой — сообщить об ошибке настройки, не превращать защищаемый деплой в обычный молча. Действующие конфиги менять не требуется.

**Что здесь значит FTP.** Сейчас панель меняет рабочую копию Git через SSH (`ajax.php`, `deploy_remote.sh`). План предполагает, что FTP-пользователь редактирует **тот же физический каталог**, что указан в `DIRS`. Тогда отдельный FTP-клиент не нужен: проверяем файлы на том же хосте через SSH. Способ внесения изменения Git не определяет — ручная правка по SSH будет замечена наравне с FTP. Если FTP ведёт в другое хранилище, режим для этой цели не включаем: проверка копии Git не защищает файлы на другом сервере.

### Автор служебных коммитов

Необязательные поля в `projects/<проект>.env` (общие для всех целей этого проекта с включённым режимом):

```ini
GIT_COMMIT_NAME=fromserver
GIT_COMMIT_EMAIL=from@server.ru
```

Если поле отсутствует или пустое, панель подставляет его значение по умолчанию из примера. Настройки применяются к автору и коммитеру создаваемых панелью коммитов: снимков правок с сервера и автоматических merge-коммитов, если слияние создаёт новый коммит. Передавать их Git только на время соответствующей операции. Глобальные `user.name` и `user.email` на хостинге настраивать или менять не нужно; авторство существующих коммитов не переписывается.

Это подпись в истории Git, а не логин для `push` и не указание на человека, который редактировал файлы через FTP. Инициатора операции панель берёт из сессии отдельно. Для целей без режима эти параметры не используются.

## 2. Поведение панели

| Выбранная цель | Что видит и делает оператор |
|---|---|
| Без режима | Дополнительных кнопок нет. «Запустить деплой» вызывает существующий сценарий с теми же параметрами; нет контроля, коммитов, push или новых требований к доступу на запись в Git. |
| С режимом → **Привязать к Git** | Кнопка остаётся на месте в обоих состояниях. Цель не привязана → **«Привязать к Git»**, обычная (не зелёная), активна; до привязки выкладка и синхронизация заблокированы. Связь подтверждена сервером → **«Привязано к Git»**, зелёная, неактивна (`disabled`); рядом показать базовый SHA, если он уже подтверждён. Особые состояния первого запуска описаны ниже. |
| С режимом → **Контроль** | Под блоком «Целевая директория» появляется кнопка. Для проверки достаточно выбрать цель, ветка не нужна. Результат: «Правок нет» либо число и относительные пути по группам «изменено / добавлено / удалено». Отдельно показываются заблокированные изменения. Ни записи в каталог, ни коммита, ни push. Ошибка чтения — не «правок нет». |
| С режимом → **Синхронизация** | Вторая кнопка фиксирует допустимые правки в Git и объединяет их **с выбранной в панели удалённой веткой**. Перед запуском показать проект, цель и ветку. Синхронизация сама **не выкладывает** содержимое ветки на сервер. Показать SHA и результат; если фиксировать нечего — без пустого коммита. |
| С режимом → **Запустить деплой** | Один запуск: контроль → при необходимости фиксация и объединение → выкладка проверенного SHA. Любая ошибка до выкладки останавливает процесс. Не переключаться на старый принудительный деплой при сбое. |

При открытии страницы и смене цели определять состояние привязки для выбранной директории. На время проверки кнопка неактивна; если статус получить не удалось, не показывать зелёный успех и не разрешать повторную привязку вслепую.

При переключении радиокнопки пересчитать видимость кнопок и очистить результат предыдущей цели. Если в проекте включена одна директория, кнопки видны при выборе именно её. На время операции зафиксировать цель и ветку в UI. Сервер проверяет проект, цель, флаг и права заново: клиент не передаёт доверенные пути. Доступ к операциям и их результатам на PROD — только у пользователей, допущенных к этой PROD-цели.

### Первичная привязка: каталог не обязан быть клоном

Привязка отвечает только на вопрос **«с каким репозиторием и какой исходной ревизией сравнивать эту цель?»**. Путь и `REPO_URL` берутся из конфига, ветка или известный SHA — из выбора оператора. Метаданные Git и запись связи держать вне web-root на хостинге: не требуется создавать публичную `.git` или клонировать репозиторий поверх сайта. Если цель ещё не клон, список веток получать из remote независимо от наличия локального `origin`. Для привязки достаточно доступа к репозиторию на чтение. Не менять remote, не делать push, checkout, reset и не записывать файлы в сайт.

| Что найдено в цели | Первое действие и дальнейшее поведение |
|---|---|
| Папка пуста (включая проверку скрытых файлов) | После подтверждения — статус **«Привязано, ожидает первой выкладки»**. Отсутствующие файлы не считать удалениями и не разрешать их синхронизацию. Первое заполнение — отдельной кнопкой существующего деплоя с указанием SHA. Под блокировкой повторно убедиться, что папка пуста и запись по FTP исключена; если уже появились файлы — остановиться и показать предпросмотр непустой цели. Базу выкладки записать только после успешной проверки результата. |
| Есть сайт, но нет Git | Сначала **только предпросмотр** относительно выбранного SHA: совпадает / отличается / только на сервере / только в Git / исключено. Не считать все расхождения ручными правками: папка могла быть собрана из другой версии или содержать лишь часть репозитория. Сохранить базу после явного подтверждения оператором исходной ревизии и состава управляемых файлов. Если база неизвестна или структура не соответствует цели — оставить статус «База не подтверждена», запретить синхронизацию и деплой. При первоначальной сверке отсутствие файла не означает разрешения удалить его из Git. Намеренные первоначальные удаления подтвердить отдельно; служебные и пользовательские данные остаются вне импорта. Первая синхронизация — отдельная операция. |
| Уже есть рабочая копия того же проекта | Проверить корень, `origin` и `HEAD`, показать найденную ревизию и незакоммиченные изменения. Принять подтверждённую базу без повторного клонирования и без очистки рабочей копии. |
| Другой `origin`, каталог внутри чужой рабочей копии, нет прав или нет выбранной ревизии | Отказ с причиной, без автоматической перепривязки и без изменения файлов. |

Подтверждение привязки требует тех же прав на цель, что деплой, CSRF-проверки и блокировки цели. Сохранять проект, реальный путь, репозиторий, точный SHA и состояние первого запуска. Повтор идентичной операции безопасен; повтор кнопки не должен сбрасывать базу и скрывать правки. Если файлы изменились после предпросмотра — запросить новую сверку. Для целей без локального `.git` далее проверять и выкладывать управляемые файлы из служебной копии, сверяя их с деревом выбранного SHA, а не требовать `git status` или `HEAD` в публичной папке. Не удалять посторонние файлы при выкладке.

## 3. Что сравниваем и как не захватить лишнее

- Для существующего клона при первом включении проверить корень рабочей копии, соответствие её `origin` репозиторию проекта и известный SHA последней выкладки. Для остальных целей применить правила первичной привязки выше. Эта ревизия — первоначальная база. **Не брать текущее содержимое FTP за эталон:** иначе уже сделанные ручные правки исчезнут из первого отчёта. Если происхождение базы установить нельзя — остановиться до подтверждения оператором.
- Сравнивать **содержимое и удаления** относительно базы этой директории, не даты файлов и не вершину выбранной ветки. Так изменения разработчиков в Git не будут ошибочно записаны как правки с FTP. Не следовать по символьным ссылкам за пределы цели.
- Учитывать изменённые и удалённые отслеживаемые файлы. Для новых неигнорируемых файлов заранее согласовать допустимые пути исходников на каждой включаемой цели. Кеш, логи, загрузки пользователей, резервные копии, `.env`, ключи и служебные файлы не отправлять в Git. `.gitignore` недостаточен: он не скрывает уже отслеживаемый секрет. Неясный новый файл, изменение запрещённого отслеживаемого файла, вложенного репозитория или неподдерживаемого типа — отдельное предупреждение и **стоп**, а не безусловное добавление или последующее затирание. Не печатать содержимое файлов в журнал.

## 4. Алгоритм для включённой цели

1. **Зафиксировать контекст.** Сервер определяет цель по конфигу, проверяет права пользователя, допустимость выбранной ветки и соответствие `origin`. Для синхронизации и деплоя взять исключительную блокировку по реальному пути цели на весь запуск. Служебное состояние и журналы хранить вне публикуемого каталога, раздельно по проекту, цели и запуску.
2. **Снять согласованный снимок.** Контроль возвращает базовый SHA и перечень отличий. При записи повторить проверку, а не использовать старый результат кнопки «Контроль». Если файл меняется во время чтения или его нельзя прочитать — остановиться. Для строгой гарантии включать режим только там, где можно временно исключить внешнюю запись на время снимка и финального обновления. Блокировка панели сама по себе FTP-клиента не блокирует.
3. **Сохранить правки отдельно от живого каталога.** В отдельной служебной рабочей копии создать коммит снимка на базе состояния, относительно которого редактировались файлы. Опубликовать его в служебной ветке данного запуска и сохранить SHA. **Не** создавать его поверх новой вершины выбранной ветки путём копирования целых файлов: это скроет реальный конфликт. В живом каталоге на этой стадии не выполнять checkout, reset или merge.
4. **Объединить в выбранную ветку.** Получить её актуальный SHA из remote; выполнить трёхстороннее слияние с сохранённым коммитом снимка в служебной копии. Если общей истории для корректного сравнения недостаточно из-за shallow-клона, догрузить её в служебной копии либо остановиться. Обновить удалённую ветку только обычным fast-forward push результата, без force. Если ветка сдвинулась — перечитать состояние и повторно проверить объединение либо остановиться, сохранив снимок. Отказ защищённой ветки не обходить.
5. **Развести синхронизацию и выкладку.** После отдельной синхронизации вывести SHA снимка и итоговый SHA ветки; файлы на FTP остаются прежними. Для каждой цели хранить отдельно SHA последней выкладки и SHA последнего принятого снимка. Новый снимок до следующей выкладки строить от предыдущего: это позволяет заметить и обратную ручную правку. Если файлы не изменились, использовать ранее сохранённый снимок без дубликата; перед деплоем проверить, что его изменения учтены **именно в выбранной ветке**, даже если ранее синхронизировали в другую. Не считать отсутствие новых файловых отличий доказательством успешного merge.
6. **Только для кнопки деплоя:** проверить отсутствие внешней записи и неизменность снимка. Если правок не было и нет ожидающего объединения — взять проверенный SHA выбранной ветки без коммита и push. Иначе выкладывать **тот SHA, который получился после успешного объединения**, а не заново запрашивать ветку по имени. Сверить контролируемые файлы с деревом итогового SHA (для локальной рабочей копии также проверить `HEAD`); лишь затем записать новую базу и показать успех. Если Git принял коммит, но выкладка не прошла, вывести два разных факта: «Правки сохранены в Git» и «Выкладка не подтверждена». Повторный запуск сверяется с remote, а не создаёт коммит повторно.

### Если Git не смог объединить изменения

Не выбирать автоматически версию «с сервера» или «из ветки». Целевую ветку не обновлять, рабочие файлы на FTP оставить как есть. Вывести имена конфликтующих файлов, выбранную ветку и ссылку или имя служебной ветки с SHA снимка. Получить этот коммит оператор должен **даже после завершения запроса**.

> Деплой остановлен: конфликт с ручными правками в `src/example.php`. Правки с FTP сохранены в `<ветка-снимок>` (`<SHA>`). Объедините этот коммит с `<выбранная-ветка>`, разрешите конфликт и отправьте результат в remote. После этого повторите деплой. Файлы на сервере не заменены.

При повторе проверить, что коммит снимка вошёл в историю выбранной ветки, затем снова опросить цель. Если с момента конфликта появились новые изменения — сохранить новый снимок поверх предыдущего. Для первой версии договориться, что конфликт разрешается **merge-коммитом с сохранением истории снимка**: squash сам по себе не подтверждает, что данный снимок принят. Если публикация даже служебной ветки невозможна, показать отдельную ошибку сохранения, не утверждать, что коммит доступен в remote, и не начинать выкладку.

### Одновременные запуски: кто может писать и когда

- **Одна физическая цель — один писатель.** Привязка, синхронизация и деплой берут одну неблокирующую блокировку на хостинге по каноническому пути (не по пользователю, вкладке или имени проекта). Блокировку брать до чтения изменяемой базы и держать до записи результата. Второй запрос получает «Цель занята» без очереди, коммита и записи в сайт. Контроль во время записи также показывает «Цель занята», а не частичный результат. Для одного хоста подходит системная блокировка `flock` на постоянном служебном файле вне сайта; не удалять файл при освобождении. Если среда не гарантирует общую блокировку для всех исполнителей, режим не включать.
- **Разные каталоги, одна ветка.** У каждого запуска своя рабочая копия и ветка снимка. Обновление целевой ветки допускается только fast-forward от проверенного состояния. Если ветка изменилась, остановиться и предложить повторную синхронизацию, без force-push. Успешный деплой привязан к конкретному SHA: более поздний push не подменяет файлы внутри уже начатой операции.
- **Писатели вне панели.** FTP, редактор на сервере, cron и старый сценарий не обязаны соблюдать `flock`. Запретить включение при пересечении управляемых путей разных целей (включая вложенные директории и ссылки), если другой путь записи не подчиняется той же блокировке. Обеспечить остановку внешней записи, включая уже открытые передачи, на критическом участке. Если это невозможно, не обещать сохранность всех правок. Для выключенных целей старый сценарий не меняется и новой защиты не получает.
- **Блокировка не делает замену файлов атомарной.** Даже один деплой поверх живых файлов может оставить смесь версий при нехватке места, обрыве процесса или ошибке записи. До PROD выбрать и проверить способ публикации на конкретном хостинге: подготовить и проверить полный релиз отдельно, затем атомарно переключить каталог сайта через поддерживаемый хостингом указатель в пределах одной файловой системы. Предыдущую версию сохранить до проверки сайта; пользовательские загрузки и конфиг не заменять. Убедиться, что и FTP, и веб-сервер после переключения видят одну актуальную цель, а блокировка привязана к **постоянному идентификатору цели**, не к сменяемому релизному пути. Если переключение недоступно — только согласованное окно обслуживания с проверенной резервной копией и восстановлением; обещания бесшовного деплоя нет.
- **Приёмка гонок.** Запустить с двух независимых сессий деплой + деплой и синхронизацию + деплой: в одной цели пишет только один процесс. Для двух целей с общей веткой проверить, что не теряется ни один принятый коммит. Прервать операцию после push, но до публикации: повтор сверяет SHA в remote и фактически опубликованную версию, не создаёт дубликата и не выдаёт неизвестный результат за успех.

## 5. Какие части менять при реализации

| Место | Изменение |
|---|---|
| `projects/*.env`, чтение настроек в `index.php` и `ajax.php` | Единое определение признака по имени цели; отсутствие ключа сохраняет прежнее поведение. Не добавлять флаг автоматически в существующие конфиги. |
| `index.php`, `accet/js/app.js` | Элементы привязки, контроля и синхронизации под целями, привязка ответа к выбранной цели, вывод статуса, SHA и списка конфликтов текстом. |
| `ajax.php` | Действия привязки (предпросмотр и подтверждение), контроля и синхронизации. В существующем `deploy` — развилка после проверки цели и прав: выключено → прежний обработчик; включено → новый сценарий. Для новых изменяющих действий проверять CSRF, код завершения процесса и таймауты. |
| Новый удалённый сценарий рядом с `deploy_remote.sh` | Общие шаги контроля, фиксации, merge и выкладки SHA; отдельная рабочая копия и журнал. Не добавлять скрытый `fetch/reset` в старый сценарий и не вызывать его заключительным шагом для защищённой цели. |

**Перед первым включением:** заменить раскрытые в поставке доступы (см. `audit.md`); проверить ключ SSH-хоста, права чтения рабочего каталога и записи только в нужный репозиторий и разрешённые ветки. Проверить, что служебную ветку сможет читать разработчик, который разрешает конфликт. Если политика ветки запрещает прямое обновление, это штатный отказ синхронизации, не повод расширять права всех проектов.

## 6. Приёмка до включения на рабочей директории

Проверить на двух тестовых целях в одном проекте и отдельном тестовом remote. Реальных серверов для проверки плана не требуется.

| Случай | Ожидаемый результат |
|---|---|
| Первичная привязка пустого каталога / сайта без Git / чужого клона | Пустая цель не создаёт коммит массового удаления; существующий сайт остаётся побайтно неизменным до и после привязки; чужой клон отклонён. Предпросмотр и подтверждение не изменяют ни ветку remote, ни файлы сайта. |
| Старый конфиг или выбрана соседняя цель без режима | Старый интерфейс и маршрут деплоя; ни одного нового сканирования, коммита или push. Ручные новые действия для этой цели отклонены. |
| Режим включён; цель чистая | Для привязанной цели доступны контроль и синхронизация. Контроль и синхронизация не меняют файлы и не создают коммит. Деплой берёт выбранную ревизию. |
| На FTP изменили, добавили и удалили допустимые файлы | Контроль показывает три изменения. Синхронизация сохраняет их в выбранной ветке без изменения FTP-каталога. Повтор без новых изменений не создаёт дубликат. |
| Изменения на FTP и в Git не пересекаются | Автодеплой сохраняет обе стороны; SHA в ответе, в remote после push и в целевой копии совпадают при отсутствии конкурентного обновления. |
| Конфликт одного файла | Есть доступный коммит ручных правок и список конфликтов; автоматическая выкладка не началась. После ручного merge и повтора развёрнут именно разрешённый вариант, а не прежняя копия с FTP. |
| FTP изменился после снимка; remote сдвинулся; push запрещён; SSH оборван | Нет принудительной перезаписи и ложного успеха. Видно, успели ли сохранить коммит, изменить ветку или начать выкладку. |
| Защищённый файл, нет прав PROD или одновременно начат второй деплой | Отказ до опасного действия; секрет не попадёт в коммит или лог, чужой журнал недоступен, конкурентная запись в каталог не начинается. |

**Первый этап внедрения:** согласовать для одной TEST-цели три вещи: что FTP и SSH видят одну директорию, какие новые файлы допустимы для Git и чем на время выкладки исключается запись по FTP. Затем реализовать и проверить сценарии выше. Для остальных директорий режим остаётся выключенным.
