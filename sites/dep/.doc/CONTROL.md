# Пилот контроля файлов: `abhaz_test`

Режим включён в рабочей копии только в `projects/abhaz.env` для `abhaz_test` (`test`). Это обновление **не устанавливалось на хостинг**. Другие проекты не включены в этот режим. Без флага сервер использует прежний путь выкладки, в том числе его прежние ограничения (см. `audit.md`). Не использовать старый обработчик или отдельный скрипт вручную для записи в защищённую цель.

## Установка обновления

Обновлять файлы прямо из `dep/` как одну версию. Основные файлы: `index.php`, `ajax.php`, `accet/js/app.js`, `accet/js/jquery-3.6.0.min.js`, `accet/css/style.css`, `control/api.php`, `control/ssh.php`, `control/project.php`, `control/branches.php`, `control/operations.php`, `control/worker.sh`, `control/inspect.sh`, `deploy_remote.sh`, `get_branches.sh`. Каких-либо `.py` файлов для работы не требуется. В существующий `projects/abhaz.env` добавить следующий блок, не заменяя остальное содержимое:

```ini
FTP_CONTROL_TARGETS=abhaz_test
GIT_COMMIT_NAME=fromserver
GIT_COMMIT_EMAIL=from@server.ru
```

**Область обратного коммита.** Синхронизация и защищённый деплой учитывают только пути из базы выкладки и сохранённого FTP-снимка, если он уже существует. Новые посторонние файлы не сканируются, не отправляются в Git и не удаляются. Если новая ветка хочет занять путь с другим посторонним файлом или папкой, деплой останавливается. Совпадающий по байтам и биту исполнения файл не перезаписывается. `.gitignore` не скрывает изменения уже отслеживаемых файлов.

**Перед push:** проверяйте список в терминале. Блокировка чувствительных имён — дополнительная проверка, а не сканер содержимого на секреты.

## Перед первым запуском

1. Заменить опубликованные ранее секреты. Сделать резервную копию сайта и проверить её восстановление. Убедиться, что каталог из конфига — именно место записи FTP и что ни одна другая панель, цель, CI или cron не публикует туда параллельно. Выключить автодеплой внешнего CI при служебных push.
2. На стороне панели: PHP 7.4+ с `proc_open` и SSH-клиент. Для карточек, списков веток по SSH и обоих вариантов выкладки используются `SSH_USER`, `SSH_HOST` и `SSH_PASS` выбранного проекта. На Linux при наличии пароля и `sshpass` панель запускает OpenSSH с передачей пароля через отдельный дескриптор (не в argv, запросе браузера или скрипте для хоста); при отсутствии помощника или пароля применяется вход по ключу. Проверка ключа хоста остаётся строгой: сверить отпечаток и `known_hosts` пользователя PHP. На Windows при настроенном пароле и доступном `plink.exe` используется `-batch -pwfile` и проверенный ключ хоста в хранилище PuTTY.
3. На стороне сайта: для **всех** операций используются Linux, Bash 4.4+, Git, `flock`, GNU findutils/coreutils (`realpath`, `sha256sum`, `stat`, `mktemp`, `mv`, `base64` и др.). Не требуются ни Python, ни PHP CLI, ни `jq` на SSH-хосте. Также нужны доступ SSH-пользователя к файлам сайта, приватный домашний каталог вне web-root и свободное место для Git-объектов и временной выкладки. Хостингу нужен доступ на чтение `REPO_URL` для Git fetch. Для push защищённой цели панель передаёт существующий `GITHUB_TOKEN` проекта по SSH на время операции; без него Git использует доступ SSH-пользователя хостинга. Резервное чтение списка веток также может передавать токен доверенному хосту. Для записи токен должен иметь права GitHub, правила веток сохраняются. Автор и коммитер задаются через `GIT_COMMIT_NAME` и `GIT_COMMIT_EMAIL`; это не криптографическая подпись.
4. Договориться об окне обслуживания: на время синхронизации и выкладки остановить запись FTP, cron и редакторов, дождаться окончания уже открытых передач. Кнопка подтверждения — подтверждение оператора, а не механизм отключения FTP. Для PROD этот вариант публикации закрыт сервером.

## Работа оператора

- **Привязать к Git.** Для непустой папки без Git указать базовый SHA или подтвердить вершину ветки, проверить предварительный список. Отсутствующие файлы требуют отдельного подтверждения. Привязка не меняет сайт и ничего не отправляет в remote. Для пустой папки первая выкладка заполняет каталог, не создавая коммита удаления. Рабочая копия с подходящим `origin` распознаётся автоматически; зелёная кнопка «Привязано к Git» отключена. На первом действии проверяется, что её `HEAD` доступен в истории remote. Для каталога без `.git` все метаданные остаются снаружи.
- **Контроль.** Вручную сравнивает пути сохранённой выкладки и выбранной ветки с файлами сайта. Отдельно показывает изменения из Git, ручные правки и коллизии. Файлы, которых нет в обоих Git-деревьях, не проверяются. База берётся из локальных Git-объектов, выбранная ветка обновляется инкрементально в `control-cache`. Список и SHA выводятся в терминал. «Контроль» не выполняет push и не меняет сайт. Синхронизация и деплой проверяют только управляемые пути для обратного коммита и отдельно проверяют коллизии при выкладке.
- **Синхронизация.** В отличие от «Контроля», коммит содержит изменения сайта относительно его последнего снимка: файл, добавленный только разработчиком в remote, не считается FTP-удалением. Дельта сохраняется в служебной ветке; merge выполняется **вне** сайта, push — без force. Конфликт показывает имена файлов и ветку снимка. Объединить её с выбранной веткой обычным merge (не squash), разрешить конфликт и повторить. Синхронизация сама не выкладывает ветку на FTP.
- **Деплой.** Та же проверка и синхронизация, затем запись проверенной ревизии. У существующего клона после публикации `HEAD` указывает непосредственно на выложенный коммит (detached HEAD). В чистой папке не создаётся публичная `.git`. Повтор без внешних изменений не создаёт новых коммитов. Запросы чтения независимы. Только одновременная запись в общие Git-данные/состояние цели отклоняется; наличие пустого файла lock не означает блокировку.

### Предпросмотр и подтверждение в терминале

Защищённая синхронизация и деплой сначала показывают в терминале цель, ветку, SHA и список файлов нового FTP-снимка, а при необходимости — список ранее сохранённого снимка. На этом этапе нет push и изменений сайта. Кнопки «Да, продолжить» и «Нет, отменить» находятся в панели терминала; тот же компонент используется для подтверждения привязки и удалений.

При подтверждении контроллер заново сверяет дерево файлов, сохранённую базу и вершину выбранной ветки. При расхождении требуется новый предпросмотр. Перед подтверждением остановите внешнюю запись. Типовые секреты, ключи, дампы и логи блокируются по имени до push, но это не полноценный сканер секретов. Предпросмотр и подтверждение всё ещё выполняются отдельными веб-запросами, не фоновой задачей.

## После сбоя

Закрытая служебная папка на хосте: `~/.dep-control/<ключ-цели>/`, где ключ — первые 24 символа SHA-256 абсолютного пути. `state.v2` — служебная запись (репозиторий, SHA базы, SHA снимка, HEAD цели, флаги пустой цели и ожидающего слияния, опубликованная ветка). Она не является скриптом. При обнаружении только `state.json` от предыдущей реализации запись останавливается до переноса подтверждённого состояния администратором. Не удалять старую базу или маркер для обхода проверки. Для целей, где предыдущий обработчик никогда не запускался, переносить ничего не нужно. Служебные ветки и записи автоматически не удаляются: следить за местом, не удалять снимок до разрешения конфликта. Изменение флага в конфиге не откатывает сайт; не выключать флаг для обхода ошибки.

Публикация на TEST обновляет файлы по одному (через временный файл и замену); **это не атомарное переключение всего сайта**. Перед первой записью создаётся `incomplete.json` с исходным состоянием и ожидаемым SHA. При обрыве он блокирует дальнейшую привязку, синхронизацию и деплой, чтобы панель не приняла собственную незавершённую выкладку за FTP-правки.

Если появился этот маркер: оставить внешнюю запись остановленной; проверить, что SSH-процесс завершился; снять копию текущих файлов и служебного состояния. Сопоставить `desired`, исходный снимок, фактические файлы и `HEAD` клона. Восстановить согласованную версию **из проверенной копии** либо завершить публикацию указанного SHA вручную, сохранив отдельные пользовательские файлы. Проверить файлы, `HEAD` и соответствие `state.v2` восстановленной базе. Только после сверки ответственный администратор снимает маркер. При неизвестном состоянии не удалять маркер и не нажимать «Деплой ещё раз». Ошибка SSH может означать потерю ответа, а не отсутствие push — проверить remote и журналы.

## Проверка сборки

`bash tests/run.sh` из корня проекта. Локальные тесты используют Bash, Git и PHP CLI, временные каталоги и bare-репозиторий. Заглушка SSH разрешает только `bash -s`; проверяются реальные Bash-сценарии и PHP-маршруты, не используются учётные данные хостинга. Доступы реального хостинга, FTP-блокировка, права файлов веб-сервера и реальный SSH-канал проверяются владельцем отдельно на TEST.

## Ветки в карточках директорий

Под каждой доступной целью на странице проекта видна отдельная строка «Ветка». Список считывается одним запросом на хост проекта (OpenSSH, проверенный ключ хоста, вход по ключу или с паролем проекта, Bash и Git, без Python), без fetch и без изменения файлов. Это требование для индикатора, а не изменение старого сценария деплоя. При отсутствии доступа карточка остаётся доступной для выбора, но показывает «не удалось проверить».

В обычной рабочей копии источником служит локальная ветка HEAD; в защищённом режиме имя сохраняется вместе с SHA только после проверки опубликованных файлов. Сама привязка или синхронизация ветку на карточке не подменяет. Пустая цель — «нет»; detached HEAD или старое состояние без подтверждённого имени — «не определена». Следующий успешный защищённый деплой сохранит недостающее имя. Маркер незавершённой выкладки отображается отдельно. Сведения обновляются при открытии страницы, возвращении на вкладку, после попытки деплоя, раз в минуту на видимой странице и вручную кнопкой «Обновить ветки». Скрытые правами директории не запрашиваются.

## Единый журнал операций панели

Общий журнал — `operations.log.php` **в корне панели, рядом с `index.php`**. PHP-пользователь должен иметь право создать этот файл или дописывать в существующий файл с корректной защитной строкой. Первая строка прекращает исполнение PHP с HTTP 404, чтобы при обычной настройке панели прямой запрос не выдавал журнал браузеру; последующие строки — JSON. Не переименовывать его в публичный `.log`. Журнал не переносится автоматически из предыдущего места. При ошибке записи смотрите стандартный PHP error log.

Формат — одна JSON-запись на строку: UTC-дата и время (`time`), пользователь сессии (`user`; до входа — `guest`), действие, статус, ID запроса и, когда применимо, проект, цель, ветка, длительность и причина ошибки. Начало и окончание запроса связаны по `id` (также заголовок `X-Operation-Id`). Для `directory_statuses` дополнительно пишется результат для каждой доступной цели. Ошибка транспорта до получения списка фиксируется на уровне запроса. Сбой браузера можно записать только если его диагностический запрос достиг панели. Для SSH не записываются сырой stderr, токен, пароль или текст запроса. Старый `lastlog.log` остаётся выводом последнего обычного деплоя, а не источником общего журнала.

Запись производится с добавлением в конец и блокировкой файла, автоматической ротации и очистки нет. Включены фоновые проверки веток и опросы журнала: следите за свободным местом. Смотреть последние события, например: `tail -n 50 operations.log.php` из каталога панели.

## Терминал в интерфейсе

«Лог выполнения терминала» общий для проверок, чтения веток, привязки, синхронизации и деплоя в этой вкладке. Время UTC и имя операции показаны в шапке блока. Фоновые проверки статуса и промежуточные проценты Git не засоряют терминал. Панель передаёт шаги в ответе текущего HTTP-запроса по мере выполнения, а не опрашивает общий `lastlog.log`. Например, видны команды SSH и Git, код завершения и сводка различий. Показываются текстовые stdout/stderr операции и команды Git с параметрами, а не только коды шагов. Внутреннее бинарное содержимое Git-объектов, индекс, протокол обмена и конфигурация с учётными данными не являются выводом для терминала. Известные значения паролей/токенов и распознанные чувствительные строки скрываются в PHP до передачи браузеру. Не включать внешние хуки/программы, которые печатают неизвестные пароли в произвольном формате. Это просмотр, не интерактивный SSH. Линии сохраняются в текущей вкладке до перезагрузки без прежнего ограничения в 500 строк.

Если прокси буферизует HTTP-ответ, строки могут появиться вместе в конце операции. Панель отправляет `X-Accel-Buffering: no`. Для обновления перенесите вместе файлы из раздела «Установка обновления»; старый JS не передаёт CSRF для обычного деплоя.

## Единые правила реализации

- `control/project.php`: чтение конфигов, разбор `DIRS` и `FTP_CONTROL_TARGETS`, права пользователя. И UI, и API используют один и тот же список `visibleTargets`.
- `control/ssh.php`: `projectSsh` — единственный запуск SSH-процесса. Любая операция получает один способ входа, проверку ключа хоста, таймаут, обработку кода выхода и поток вывода. Локальная оболочка PHP не разбирает строку SSH-команды.
- `control/branches.php`: общий список веток для всех директорий. GitHub GraphQL с постраничной загрузкой; при недоступности — `get_branches.sh` через тот же `projectSsh`. Кэш разрешён только для рабочего каталога нужного `origin` и отмечен в терминале.
- Кнопка деплоя всегда обращается к `deploy`. Сервер сначала проверяет проект, права на цель и токен сессии, затем по конфигу вызывает обычный `deploy_remote.sh` или `control/worker.sh`. Обычный сценарий не создаёт файлов состояния FTP и не делает push. Для контролируемой цели не предусмотрен молчаливый переход на обычную принудительную выкладку.

### Если последним запросом оказался `fc_status`

Карточка и проверка привязки не берут и не проверяют `flock`. Контроль и предпросмотр выполняются в отдельных временных Git-репозиториях и не меняют общие refs, индекс или состояние. Две проверки из разных окон не резервируют каталог. Только операции записи (`bind`, подтверждённые `sync` и `deploy`) взаимоисключающие. Предпросмотр не берёт блокировку и использует отдельный временный репозиторий. Не удаляйте lock-файл: это не способ освободить системную блокировку. Если запись уже началась и есть маркер `incomplete.json`, нужна сверка согласно разделу «После сбоя». Журнал отмечает успешный результат контроля как `comparison: clean` или `changed`.

**Повторная выкладка.** Если SHA и дерево уже совпадают и нет ожидающих правок, операция заканчивается без подтверждения после одной сверки. Если SHA другой, а дерево совпадает, после подтверждения обновляются только метаданные. Для обычной защищённой выкладки итоговое дерево и каталог проверяются до push; при конфликте merge отправляется только служебный снимок для ручного разрешения. Фоновой очереди и долговременного хранения предпросмотра пока нет.
